## Sampling-count expansion and optimization

The central scaling problem is cubic growth. If the number of samples along each axis doubles, density work and storage grow by approximately eight times:

```text
samples ≈ (cells per axis + 1)³
```

The earlier voxel preview also rendered 12 triangles for every solid sample, including fully hidden internal faces. That approach was useful for learning density fields but became wasteful as the finite world expanded.

The current design makes four targeted improvements:

- It stores density once in a `Float32Array` and lets every mesher read the same field. Comparing three algorithms no longer evaluates the SDF three separate times.
- It adds only a one-sample halo around the finite field. The halo supplies consistent central-difference normals at chunk boundaries without each chunk creating a private padded volume.
- It replaces filled voxel cubes with extracted surface triangles, removing most internal geometry.
- It separates sampling time from meshing time. Increasing pixel/sample density can now be diagnosed as SDF cost, meshing cost, or output-buffer cost instead of one combined number.

For the default 3 × 3 × 3 chunks, 12 cells per chunk, and spacing 0.5, the world contains 36 cells per axis. The shared halo buffer uses 59,319 floats, or 237,276 bytes. Reducing spacing while holding the world size fixed raises the cell count in all three axes and is therefore the most expensive quality control.

## Shared density and chunk seams

All algorithms use one world-coordinate density field and iso-value zero. Every chunk owns a fixed cell range. Marching Cubes and Marching Tetrahedra own cells directly. Surface Nets assigns every sign-changing grid-edge face to one canonical incident cell, which maps to exactly one chunk. Neighboring Surface Nets vertex positions may be recomputed, but they read identical density samples and do not duplicate face ownership.

Normals are generated after vertex placement from the same trilinearly sampled density buffer. Tests compare adjacent chunk vertices and normals. Surface Nets uses shared cell-vertex comparison because its representative vertices are inside cells and are not required to lie on the chunk boundary plane.

## Meshing comparison

The following Node.js measurements used the default chunk-cave preset, one warm-up, five measured runs, and the median. They are useful for relative comparison on this machine; browser timing can differ.

| Algorithm | Median mesh time | Vertices | Triangles | Mesh buffers | Density + mesh |
| --- | ---: | ---: | ---: | ---: | ---: |
| Marching Cubes | 17.867 ms | 15,240 | 5,080 | 365,760 B | 603,036 B |
| Surface Nets | 19.981 ms | 15,216 | 5,072 | 365,184 B | 602,460 B |
| Marching Tetrahedra | 63.631 ms | 47,904 | 15,968 | 1,149,696 B | 1,386,972 B |

Shared density sampling median: **7.315 ms**.

Observed tradeoffs:

- Marching Cubes was fastest in this run and produced a smooth, conventional interpolated surface with moderate output size.
- Basic Surface Nets produced almost the same triangle and buffer counts because this teaching implementation emits non-indexed triangles. Its conceptual one-vertex-per-active-cell advantage will require indexed vertex sharing to become a clear memory advantage. Its cell-centered placement gives a more block-aware silhouette.
- Marching Tetrahedra was about 3.6 times slower than Marching Cubes in this run and emitted about 3.1 times as many triangles. Its implementation avoids cube-case ambiguity by applying one consistent six-tetrahedron split, but pays for that simplicity with more work and data.

These figures are not universal performance claims. Shape topology, JavaScript engine, browser, CPU, sampling resolution, and future indexing can change the ranking.

```text

        ↓

        ↓

        ↓
```
